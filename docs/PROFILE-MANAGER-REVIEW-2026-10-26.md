# Mod Profile Activation Manager review — 2026-10-26

Two retained personal game-specific helpers supplied the general enable/disable
use case. Their original bytes remain unchanged in a private provenance record.
This publication is a new original bounded managed-workspace application with
CLI and optional Tk desktop, first-party MIT helper reuse, authored guides/tests
and fictional fixtures. No original helper body, actual game/mod content, old
manifests, game-specific configuration, private runtime store or held source is
included. The original implementation and authored materials are offered under
MIT; imported inputs retain their own rights.

Local Windows CPython 3.12.7 / Tk 8.6.13 validation discovered 118 unittest
methods: **110 passed, 8 platform/environment skips**, no failures
or errors. Skips are not passes. Checks cover real generated file operations,
strict manifests and limits, drift refusal, native locking and no-replace rename,
actual subprocess interruption and fresh-process recovery, optimized-Python
guards, CLI exits/privacy and hidden native Tk widgets. The desktop tests include
a generated engine lifecycle. These are not live game or power-loss tests.
Windows/Ubuntu CI is configured in four Python 3.12/3.13/3.14 jobs; consult Actions
for observed matrix outcomes rather than treating configuration as test evidence.

A separate documented CLI walkthrough ran 12 commands using four generated text
files: initialized a new workspace, imported orchard/meadow, planned/activated,
switched, deactivated, listed and checked idle recovery. The four source files
remained byte-identical and both old active trees remained retained. This smoke
run is separate from the unittest method count.

The manager controls only its own workspace. Activation changes its fixed active
folder, with verified staging, native locking, no-replace directory commits,
retained previous trees and explicit observed-state recovery. It does not detect,
launch or configure games, manage saves, edit profile contents, purge old trees,
or prove compatibility with any loader. Game integration is manual and dependent
on the loader. No installed game or valuable project directory was deployed to.

Detailed guides cover installation, Windows/Linux commands, desktop actions,
expected results, exact file/path/size/count bounds, state schemas, interruption
recovery, refusal codes, storage requirements, privacy and provenance. Two
dedicated community forms accept bug reports and suggestions using fictional
examples. The desktop shows readable summaries and offers structured details.

Operational state includes relative names, hashes, counts, profile IDs and random
operation IDs. It stays private outside the source checkout and is not anonymous.
No actual personal data or identifying runtime metadata is bundled. Ordinary
source/commit metadata and required MIT notices remain. Public examples are
invented text, not installable mods. Byte verification is consistency evidence,
not proof of input ownership, authenticity or distribution rights.

Supported inputs are quiescent local regular-file trees in trusted parents. The
implementation refuses unsupported links, streams, paths and bounds. It is not
a hostile-filesystem sandbox or a host-independent snapshot. Hash/readback and
requested flushes do not prove power-loss durability. Retained/partial work
consumes disk; the application has no automatic cleanup. Unknown or inconsistent
recovery state remains held rather than being overwritten.

Publication uses an explicit source-only allowlist, exact SHA-256 manifests,
manual provenance/scope review, privacy-pattern scanning and canonical Git-blob
readback. Pattern scans do not prove absence of every secret or exclusive
historical authorship. This publication does not clear any unrelated held
employer/client source. Python/Tk/native APIs remain separately supplied under
their applicable terms; no runtime or upstream implementation is bundled.
