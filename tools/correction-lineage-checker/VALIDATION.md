# Validation and limits

The review-change-checks workflow qualifies Python 3.12/3.13 on Windows and Ubuntu.
Native hardlink, linked-parent, changed-input, new-file and overwrite fixtures are
required. Only opposite-platform methods may skip; local volume skips are not native proof.

Known-answer/adversarial tests check exact review coverage/blockers, stale pins, queue
ambiguity, stage non-authority; complete revision chains, missing roots/parents, gaps,
forks, unchanged/cross-record/non-successor edges; exact approval/revocation boundaries,
future events, reviewer/role scope, policy pins, reapproval and input order; directional
transitive impact, multiple roots, diamonds, disconnected cycles, stale bindings and
a 700-node iterative chain. Every identity list checks duplicate/conflict/rejected-row
accounting and scope withholding; bounded public I/O and JSON helpers retain their tests.

Actual standalone acceptance copies each directory separately, checks source pins,
runs examples, writes fresh reports, refuses overwrite/source output, checks fixed
errors and raw-input pins, and verifies unchanged inputs/no target artifacts. A connected
invented HVAC service exercise reviews a correction chain, explicitly adapts its selected
revision into approval/queue snapshots, derives role coverage from declared active grants,
and checks downstream recheck IDs. Counter-examples revoke one exact grant, explicitly
recheck queue coverage and refuse a stale graph. An invented game quest fixture contains
only metadata. No automatic approval transfer or hidden runtime dependency is implied.

Synthetic tests do not establish authentic histories, real reviewer identity/authority,
correct real policies, complete real dependencies, actual review, physical service,
production suitability, privacy or rights. Original private implementations, schemas,
policies, documents, logs, records, paths, credentials and operational details were not
consulted or selected. No real record change, notification, approval or execution.
