# Validation and interpretation limits

The routing-integrity-checks workflow qualifies Python 3.12/3.13 on Windows and Ubuntu,
requiring native hardlink, linked-parent, changed-input, new-file and overwrite checks.
Only opposite-platform methods may skip; local volume skips are not native proof.

Known-answer/adversarial cases cover normalized capability declarations, separate
versus summed budgets, exact threshold equality, full request coverage, stale model/
request/prompt/policy pins and ambiguous assignments; explicit fallback traversal,
cycles/unreachable steps, transition condition schemas, repeated models, complete
32-step chains and cap failures without truncation; recomputed plan bindings,
contiguous receipts, forbidden retries after success/uncertainty, permitted failure
conditions, early success, terminal failure, missing fallback evidence, explicit unknown
outcomes, output-budget review and every declared-result mismatch.

Standalone CLI acceptance copies each complete directory independently, verifies source
pins, runs examples, creates fresh reports, refuses overwrite/source-tree output,
checks raw input pins/fixed errors and verifies no input mutation or target artifacts.
A connected invented HVAC flow checks two model declarations, one explicit request
assignment, a two-step timeout/unavailable fallback and two supplied receipts. It
reconciles a recorded primary timeout and reserve success, without invoking either.
A separate game NPC routing fixture remains hypothetical. A counterexample confirms
consistent model declarations do not make an oversized request eligible.

These are synthetic functional checks of explicit declarations, not real model support,
availability, measured tokenization/cost/latency, authentic provider receipts, actual
inference, correct output content, privacy, rights or production suitability. Original
private code, schemas, routing policies, prompts, records, models, configurations and
assets were not consulted or selected. No providers, weights, payloads or endpoints.
